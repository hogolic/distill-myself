## 🔴 第一条铁律（优先于下面所有规矩）

**可以增加文件、修改文件、移动文件 —— 但不能删除文件。**

| 动作 | 权限 |
|---|---|
| 新建、修改、移动、重命名 | ✅ 可以直接做 |
| **删除** | ❌ **不行。** 需要"删掉"的东西 → **移到 `99-归档 Archive/`** |

**为什么这条排第一**：增、改、移都能回滚（git 有记录），**删除不能**。
尤其是 `00-收件箱 Inbox/` 里那些**还没被提交过的草稿** —— 删掉就是永久消失，git 里也找不回来。

> 真删除只有本人能做。

## 硬规矩（不用问，直接守）

### 一、目录就是 PARA，判据只有一条

| 目录 | 放什么 | 判据 |
|---|---|---|
| `00-收件箱 Inbox` | 想到什么先扔进来 | **不确定放哪的全在这** |
| `10-项目 Projects` | 有终点的事 | **做完会结项** |
| `20-领域 Areas` | 没终点的事 | 没有「做完」那一天 |
| `30-知识 Knowledge` | 经过理解、备查的东西 | 别人的原文 + 自己的理解 |
| `40-日记 Journal` | 按时间记的 | 不进分类体系 |
| `90-模板 Templates` | 模板 | 工具目录，不写内容 |
| `91-附件 Attachments` | 图片、PDF | 工具目录 |
| `99-归档 Archive` | 已结束 / 暂停的 | **不删，只移过来** |

**分不清 Projects 和 Areas 时，只问一句：这件事有终点吗？**

### 二、每篇笔记开头写 front matter

```yaml
---
title: 一句话说清这篇讲什么
tags: [标签1, 标签2]
source: 外部资料必填出处；自己写的留空
created: YYYY-MM-DD
status: 草稿 | 待核对 | 已整理
---
```

**这五个字段之外，不要自己加字段。**
如果本人自己加了（比如 `对话链接`），**不要动它** —— 那是他特意设计的，不是不规范。

### 三、文件命名

- 笔记：直接用中文标题，如 `高位下拉的握距区别.md`
- 日记：`YYYY-MM-DD.md`
- 外部资料：`标题 - 来源.md`
- **不要** `新建笔记1.md`、`未命名.md` 这类名字

## 不要做的事

- ❌ **不要建空壳笔记** —— 否则库会变成「AI 生成内容的堆积」
- ❌ **不要过度设计** —— 不要一次性建一堆目录、模板、索引
- ❌ **不要擅自重构目录或批量移动文件** —— 要动先写清「动什么、为什么」，等确认
- ❌ **不要把别人的原文和他自己的推测混在一起** —— 靠 `source` 字段分清
- ❌ **不要把外部项目的源码拷进库** —— 只记 **GitHub 地址 + commit 号**。
  源码会过期、撑大体积、撑爆网盘同步；嵌套 `.git` 还会被外层当成 gitlink（clone 下来是空文件夹）
- ❌ **不要动他自己加的 front matter 字段**
  > 规范是给没想法的地方用的，**他已经想过的地方不要覆盖**
- ❌ **不要做周报 / 复盘 / 周期总结类产出**，除非他明确要 —— 他要的是可执行的下一步

## 协作（如果有多个 AI 同时在写）

**动手前后各一步：**

```bash
git status          # 动手前：看有没有未提交的改动
git diff HEAD       # 写完：复核改动，确认没有意外删除
```

**四个最致命的坑：**

1. **Obsidian 开着的时候改文件，编辑器会把旧内容存回去**
   → 改完必须 `git diff HEAD` 看一眼；那文件正开着就让他切个文件或重启
2. **看到大段删除，先问「谁删的」，别急着恢复**
   → 可能是有人的判断变了，不是事故。`git checkout` 看似安全，实际会覆盖别人的决定
3. **`.gitignore` 不管已跟踪的文件** → 要 `git rm --cached <文件>` 才真正生效
4. **Git Bash 的 heredoc 会吃掉 Python 正则的反斜杠**
   → 含正则或反斜杠的脚本，**写成 `.py` 文件再执行**，别用 heredoc
