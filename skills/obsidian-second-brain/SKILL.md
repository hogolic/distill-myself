# 搭一个 AI 能维护的第二大脑

你的任务：帮用户把一堆散乱的笔记（或零笔记）变成一个 **PARA 结构 + AI 可维护**的 Obsidian 库。

**核心不是建目录，是定两条规矩。** 目录 30 分钟能建完，规矩定不对，三个月后它会变成垃圾场。

---

## 开始之前：先问这 4 个问题

不要一上来就建目录。先问清：

1. **你现在有多少笔记？** 零 / 几十 / 几百（决定要不要做迁移）

> ⚠️ **如果用户已经有几百篇散落笔记**：不要帮他一次性分类 —— 那会劝退他。
> 按 README「进阶一」的三步走：**全倒进 Inbox → 只挑这个月用过的 → 其余归档**。
> **不要给旧笔记批量补 front matter。**
2. **你在长期维持哪几件事？** （英语？健身？写代码？—— 这些进 `20-领域 Areas`）
3. **你手上正在做的、有终点的事是什么？** （—— 进 `10-项目 Projects`）
4. **你想让 AI 帮你做什么？** 整理？查资料？写笔记？（—— 决定 AGENTS 写多细）

**如果用户说"不知道"，就用默认答案，开始做。别卡在提问上。**

---

## 第一步：建骨架（只建 4 个目录）

```
00-收件箱 Inbox/
20-领域 Areas/
40-日记 Journal/
90-模板 Templates/
```

**不要一次建九个。** 用户的反馈通常是"看着有点乱"—— 目录越多越乱。

等真的出现了"有终点的项目"，再加 `10-项目 Projects/`；真的有东西结束了，再加 `99-归档 Archive/`。

### 命名规则（必须坚持）

**数字前缀 + 中文 + 空格 + 英文**：

```
00-收件箱 Inbox
20-领域 Areas
40-日记 Journal
```

- 中文在前（用户母语读得快）
- 英文在后（对应 PARA 术语）
- **数字必须两位以上**（否则 10 会排在 9 前面）

> 如果用户库里已有 `20-Areas` 这种纯英文的，**问要不要改成双文**，不要擅自改。

### 同时放入三个模板（别自己发明结构）

`90-模板 Templates/` 里放这三个。**手边有仓库的 `templates/` 目录就直接复制那三个文件**；没有就按下面的结构写：

| 文件 | 结构 |
|---|---|
| `笔记模板.md` | 五字段 front matter + 一行 `# {{title}}` |
| `日记模板.md` | 五字段 front matter（`tags: [日记]`）+ `# {{date:YYYY-MM-DD}}` + 四节：开心的事 / 不开心的事 / 今日的所思所想 / 和 AI 聊完之后的总结 |
| `资料模板.md` | 五字段 front matter（`tags: [资料]`）+ 来源 / 作者出处 / 读它的原因 + 核心内容 / 我的判断 / 关联 |

front matter 照第二步那份抄，`status` 一律先写 `草稿`。

> ⚠️ `{{date:YYYY-MM-DD}}` 和 `{{title}}` 是 Obsidian 模板语法，模板插件启用时才会替换。
> 用记事本打开看到原样占位符是正常的，别去"修"它。

---

## 第二步：写 `README.md`（讲结构和写法）

**要现成的完整版，就改仓库里的 `boilerplate/README.md`；没有则按下面七块写。**

这是给**人和 AI**看的。内容：

1. **这个库是什么**（一句话）
2. **🔴 唯一一条铁律：不能删**（见第三步，重复一遍是故意的）
3. **目录结构表**：每个目录放什么 + 判据
4. **front matter 规范**：五个字段
5. **文件命名**
6. **日常工作流**
7. **双链怎么用**

### front matter（五个字段，一个都别多）

```yaml
---
title: 一句话说清这篇讲什么
tags: [标签1, 标签2]
source: 外部资料必填出处；自己写的留空
created: YYYY-MM-DD
status: 草稿 | 待核对 | 已整理
---
```

**`status` 三选一很重要** —— 它能让用户一眼筛出"没写完"和"需要我过目"的东西。

> ⚠️ **如果用户自己加了非标准字段（比如 `对话链接`），不要动它。**
> 那是他特意设计的，不是不规范。**规范是给没想法的地方用的。**

---

## 第三步：写 `AGENTS.md`（讲规矩）

**要现成的完整版，就改仓库里的 `boilerplate/AGENTS.md`。**

这是给 **AI** 看的。**第一条必须是删除限制**：

```markdown
## 🔴 第一条铁律（优先于下面所有规矩）

**可以增加文件、修改文件、移动文件 —— 但不能删除文件。**

| 动作 | 权限 |
|---|---|
| 新建、修改、移动、重命名 | ✅ 可以直接做 |
| **删除** | ❌ 不行。需要"删掉"的东西 → 移到 99-归档 Archive/ |
```

**为什么这条排第一**：增、改、移都能回滚（git 有记录），删除不能。
尤其是收件箱里**还没被提交过的草稿** —— 删掉就是永久消失。

### 还必须写进去的

```markdown
## 不要做的事

- ❌ 不要建空壳笔记 —— 否则库会变成 AI 生成内容的垃圾场
- ❌ 不要一次性建一堆目录、模板、索引 —— 过度设计比不做更糟
- ❌ 不要擅自重构目录或批量移动文件 —— 要动先写清"动什么、为什么"
- ❌ 不要把源码 clone 进库 —— 只记 GitHub 地址 + commit 号
- ❌ 不要把别人的原文和用户自己的推测混在一起 —— 靠 source 字段分清
- ❌ 不要动用户自己加的 front matter 字段
```

### 协作部分（如果有多个 AI）

```markdown
**动手前后各一步：**
- 前：`git status`（看有没有别的会话留下的未提交改动）
- 后：`git diff HEAD`（复核改动，确认没有意外删除）

**四个最致命的坑：**
1. Obsidian 开着时改文件，编辑器会把旧内容存回去 → 改完必须 git diff 看一眼
2. 看到大段删除，先问「谁删的」，别急着恢复 —— 可能是用户的判断变了
3. .gitignore 不管已跟踪的文件 → 要 git rm --cached 才生效
4. Git Bash 的 heredoc 会吃掉 Python 正则的反斜杠 → 含正则的脚本写成 .py 文件再跑
```

## 第四步：装 git（不可跳过）

```bash
git init
git add -A
git commit -m "init: 第二大脑骨架"
```

**没有 git 的知识库，删错了就真没了。** 这不是可选项。

如果用户要跨设备，再教他推到 GitHub 私有仓库。

---

## 第五步：让用户写第一篇日记

**这是唯一不能跳的一步。**

不要等他"准备好了"。现在就建 `40-日记 Journal/YYYY-MM-DD.md`，用模板，**让他随便写一行**。

**判断项目成功与否的标准不是目录建得多好，是明天他还写不写。**

---

## 按需扩展（别提前做）

用户有需求时再加，**不要主动建**：

| 用户说 | 加什么 |
|---|---|
| "我有正在做的项目" | `10-项目 Projects/` + 一篇项目笔记（目标/进展/卡在哪） |
| "东西太多了想清理" | `99-归档 Archive/` |
| "我想收藏工具" | `30-知识 Knowledge/工具清单.md`（一张表，**必须有「用过吗」这一列**） |
| "我想放图片" | `91-附件 Attachments/`（Obsidian 设置里指定） |
| "我想在手机上也能记" | **坚果云同步插件 `Nutstore Sync`**（Obsidian 社区插件）。⚠️ 装完先确认「自动同步时删除前确认」= 开（默认就是开）、同步 `.obsidian` = 关。官方教程 <https://blog.jianguoyun.com/?p=6104> |
| "我想和自己的另一面分开" | `100-我自己 Myself/`（见下） |

### 关于 `100-我自己 Myself`（可选，但很特别）

如果用户既想存知识、又想留下"自己是怎么变的"，建议开这个目录。

它**不属于 PARA** —— PARA 按「事情的性质」分，它按「关于谁」分。

> PARA 回答「这东西放哪」，Myself 回答「我是谁」。
> 前者是仓库，后者是镜子。

编号用 `100` 是为了排在 99 之后，**视觉上隔开**。

里面放：个人说明书 / 经历叙事 / 事实盘点 / 他人视角。
**他人视角必须各自独立成篇，不要合并成一份"权威档案"** —— 不同来源看到的侧面不同，合成一份会丢掉差异。

## 给 AI 的检查清单

做完之后逐条确认，**全部打勾才算完成**：

- [ ] 顶级目录 ≤ 5 个（超过就是过度设计，砍掉）
- [ ] 目录名是"数字 + 中文 + 空格 + 英文"，且数字两位数
- [ ] `README.md` 里有：目录结构表 / front matter 表 / 命名规则 / 日常工作流
- [ ] `AGENTS.md` **第一条是删除限制**
- [ ] `AGENTS.md` 写了「不建空壳笔记」「不过度设计」
- [ ] `90-模板 Templates/` 里至少两个模板，且 Obsidian 里配好了模板文件夹
- [ ] Obsidian 里配好了日记文件夹（`40-日记 Journal`）和附件文件夹（`91-附件 Attachments`）
- [ ] git 已初始化，有第一次提交
- [ ] 用户今天写了一条日记（哪怕一行）
- [ ] **库里没有任何空壳笔记**（0 字节的文件补上内容，或移到 `99-归档 Archive/` —— **不许删**）

> 📌 **本清单与 README 的「做完之后逐条确认」是同一份。** 改一处，记得同步另一处。

## 最常见的三次翻车

### ① 一次建太多

建了九个目录、五个模板、三个索引，用户看了说"太复杂"，然后不用了。

**解法：只建 4 个目录，让目录自己长出来。**

### ② 规则写成散文

写了三千字"知识管理哲学"，AI 读了不知道具体该干什么。

**解法：规矩必须是表格或命令。** 「能增能改不能删」比「请谨慎处理用户数据」有用一百倍。

### ③ 让 AI 自动整理

用户开了自动整理，一个月后库里有 150 篇 AI 写的、自己一篇没读过的笔记。

**解法：AI 只能**建议**，不能**代替判断**。
「这条要不要归档」必须问用户，不能自己决定。

架子搭完就停手 —— **剩下的靠他写，不靠你建。**
